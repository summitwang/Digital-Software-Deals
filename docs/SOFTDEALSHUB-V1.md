# SoftDealsHub 新版 V1 实施基线

## 目标与范围

英文手机优先商城、中文运营后台。自营零售与代理专属价格并行，付款确认与人工审核交付分开。独立链接工具继续独立运行。暂不优化 OCR、不切换 Telegram CID 上游、不接入供应商付费 OCR。

## 架构决定

- 延续 Next.js + Vercel；商务逻辑集中在服务端，不信任浏览器传来的金额、交付类型、订单归属。
- Supabase PostgreSQL 存储商品规格、订单行、付款事件、库存单件、交付记录、售后及审计日志；Auth 管理买家身份。
- 付款截图与售后附件使用私有 Storage，通过鉴权后的短时签名地址访问。
- 邮件与供应商任务采用事务 outbox + 持久化 worker；任务重试必须幂等。执行平台与费用待实际负载和部署权限盘点后确定。
- 测试和生产数据隔离；Preview 不使用生产写入凭据。生产数据库与 Storage 文件分别备份并演练恢复。

## 核心模型

| 实体 | 职责 |
| --- | --- |
| products / variants | 软件、系统、地区、设备数、时长、资格要求、价格和交付规则 |
| orders / order_items | 订单及成交快照；每行独立计价和履约 |
| payments / payment_events | 支付平台事件唯一键、金额币种核对、退款与异常 |
| inventory_units / reservations | 单件密钥或账号、批次、预留期限与分配归属 |
| fulfillments | 密钥、账号、邮箱开通、人工服务；部分交付及补发历史 |
| tickets / audit_events | 售后及敏感操作审计 |
| agent_prices | 代理价格和批量采购；钱包暂不与机器人重复建设 |
| outbox / jobs | 可靠通知、交付、重试与失败队列 |

库存预留、订单写入必须同一数据库事务；支付迟到、缺货、少付等进入异常队列。订单、付款、交付状态独立，禁止回调覆盖已完成交付。

## 页面与操作

买家：首页搜索和分类 → 商品规格与兼容性 → 购物车 → 邮箱/账户结账 → 付款及审核进度 → 私密交付页 → 售后与教程。

后台：待审核、待发货、待补资料、交付失败、低库存、售后；商品规格管理、采购批次、逐件交付、补发、退款记录、代理价格及报表。

订阅期限和售后保障期限分别保存、展示；不展示无依据的评价分数或即时发货承诺。

## 验收与限制

本次纯函数测试覆盖正常促销计价、改价、过期报价、非法数量、缺货、无促销价及非法金额。执行 `node --test tests/checkoutPricing.test.mjs`（Node 24）。

必须另做隔离数据库与路由集成测试：确保金额失败不会创建支付单、上传附件或写库存；验证最后一件库存并发、同一付款重复回调、访客/他人越权、部分交付、补发退款及邮件失败重试。

当前未连接生产数据库、未执行迁移、未验证 Vercel Preview、未测试真实支付；现存库存竞争和查单权限问题尚未修复，不能把本次提交视为完整上线验收。构建使用虚拟环境变量只验证编译，不验证后端服务。

## 第二批：订单访问与回调签名

已在代码中增加订单读取/售后提交的身份验证。绑定订单仅允许原 user_id；未绑定游客订单要求同邮箱且邮箱已验证。客户订单列表拆分查询，避免将邮箱插入 PostgREST 表达式，也不再允许邮箱匹配访问其他用户已绑定订单。私密订单响应禁止缓存。

Track Order 增加 Supabase 邮箱登录入口，接回真实会话令牌。上线前必须配置并验收 Supabase Site URL / Redirect URLs 中的正式与 Preview `/track` 地址、邮件服务和登录链接模板；目前未发送真实邮件。已有同邮箱账号可直接登录。游客历史邮箱大小写不规范数据需在迁移时核对（列表目前使用精确邮箱匹配）。

支付回调未配置 IPN secret 时返回 503；无效签名返回 401，采用固定长度校验及 timingSafeEqual。签名单元测试使用合成载荷，真实供应商嵌套载荷兼容性仍需联调。

本轮总计 13 项单元测试通过。订单归属策略、签名校验和计价通过，不等于数据库 RLS、管理员接口、真实邮件或支付链路已完成验收。库存事务、回调幂等及状态单调推进仍未实现，需继续开发。禁止将此草稿直接作为完成版发布。

## 第三批：数据库事务与回调幂等（覆盖此前未实现状态）

新增 `supabase/migrations/202611150001_order_transactions.sql`，手动付款订单通过 `create_verified_order_v1` 在同一事务核验当前价格、条件扣减库存、写订单；插入失败自动回滚。新增订单使用随机 UUID；TxID 大小写不敏感唯一。已核验链上凭证的订单仍保留 pending_verify 人工审核。

`apply_payment_v1` 使用支付标识事务锁、订单行锁、事件唯一约束和条件库存扣减；核对支付平台、invoice ID、订单金额及 USD 币种。重复事件不再扣库存，旧状态通知不回退支付成功状态，不覆盖已交付业务状态或 delivery_note。付款后缺货进入 problem，stock_deducted 保持 false，等待人工处理；退款不自动回收已交付库存。

隔离 PGlite 数据库基于源码推导的最小表结构执行真实 SQL：11 项事务测试通过，加上原有 13 项共 24 项。最后一件库存的两个并行调用只能成功一个，但 PGlite 单连接内部串行执行，此结果不能替代真实 PostgreSQL 多连接竞争与死锁测试。

发布顺序：核对真实 orders/products 类型、默认值、RLS、触发器及历史重复订单号/TxID → 在独立 Supabase 测试库执行迁移 → 完成多连接并发、真实支付事件及邮件验收 → 先部署兼容数据库函数再部署应用。不得只部署应用而缺少 RPC。迁移失败会整体回滚；发现历史重复记录时先人工核对，禁止自动删除。

仍待完成：商品 ID 绑定替代标题查找、库存预留过期释放、付款前发票创建幂等/持久化、私有截图及失败上传清理、管理员写入路径统一事务、缺货异常处理入口、实际供应商事件格式验证（包括 invoice_id 和金额字段）。本轮没有连接或修改生产数据库。当前 SQL 的兼容性以推导测试表为限，尚未获得真实生产 schema。

## 第四批：商品 ID 结账与后台交付校验

首页、商品详情及商品列表统一传递 productId。付款页通过只返回公开结账字段的 `/api/checkout-product` 读取当前价格和库存，不再信任 URL 的金额/库存；缺货或读取失败禁用付款。旧标题链接仅在标题唯一时解析，随后用 ID 提交。新订单持久化 product_ref（文本兼容现有 ID 类型）；支付回调按 ID 找库存，商品改名后仍可处理。历史无 ID 订单仅允许唯一标题匹配，不自动回填。

后台 admin-orders 的更新改用 update_order_delivery_v1：锁定订单后校验，库存未落实或付款已退款/失败/过期时不能直接标为已发货，重复发货不再次扣库存。缺少 ADMIN_PASSWORD 时拒绝后台请求。当前仍是现有密码鉴权，不代表管理员角色、会话和审计工程已经完成。

累计 28 项测试通过，新增改名/同名商品隔离、无 ID 拒绝、后台缺货拦截及重复交付测试。页面和真实邮件/付款尚未完成浏览器联调。SQL 仍为未部署草稿，本轮更新同一个迁移文件；如果任何环境曾手动执行旧草稿，必须对照补列并重建函数，不能假定迁移工具会重跑同名迁移。

剩余：完整管理员权限和操作审计、付款异常人工恢复入口、库存预留、发票幂等、私有附件、真实 schema/多连接并发验证、新版统一 UI。当前代码不得直接切换生产。
